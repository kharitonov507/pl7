# Player Control — демонстрационный стенд

Нейтральное рабочее название пилотной системы управления сетью экранов. Существующий живой стенд с тремя Go-плеерами сохранён, а `/fleet.html` добавляет масштабируемый реестр локальных и импортированных устройств.

## Реестр 100 экранов и адаптер внешней CMS

- `http://127.0.0.1:8787/fleet.html?demo=100` показывает непостоянную симуляцию 100 экранов с поиском, фильтрами и пагинацией. Это проверка интерфейса, не нагрузочный тест физических устройств.
- `http://127.0.0.1:8787/fleet.html` показывает реальные локальные устройства и дисплеи, импортированные из подключённой CMS.
- Адаптер авторизуется по OAuth2 client credentials, читает дисплеи, медиатеку, раскладки и расписания, а также загружает изображения и видео из нейтрального интерфейса Player Control. Локальные неиспользуемые медиа и плейлисты можно удалять; прямое удаление объектов во внешнем сервере намеренно не включено в демонстрационный режим.
- Для локального Xibo допустим `http://127.0.0.1:8088`; удалённая CMS обязана использовать HTTPS.

Перед запуском скопируйте `.env.example` как `.env.local`, заполните значения и не пересылайте этот файл. `start-go-demo.cmd` загрузит его автоматически:

```text
XIBO_BASE_URL=http://127.0.0.1:8088
XIBO_CLIENT_ID=<идентификатор приложения CMS>
XIBO_CLIENT_SECRET=<секрет приложения CMS>
```

После запуска откройте реестр и нажмите «Синхронизировать CMS». В интерфейс и ответы статуса client secret не попадает. Адрес `:8088` считается технической панелью внешнего движка; для демонстрации и ежедневной работы используется только нейтральный интерфейс Player Control на `:8787`.

Импортированные каталоги доступны в интерфейсе по адресу `http://127.0.0.1:8787/catalog.html` и через `GET /api/integrations/xibo/catalog` с необязательными параметрами `kind`, `q`, `page` и `pageSize`. Кнопка «Добавить медиа» отправляет JPG, PNG, WebP, MP4 или WebM (до 1 ГБ) в медиатеку серверной CMS и сразу обновляет локальный снимок. Исходные файлы из внешней CMS пока не копируются в кеш Go-плеера, а сложная раскладка ещё не преобразуется в локальный плейлист.

**Обновление 0.2:** реализован отдельный нативный Go-агент. Запуск — `start-go-demo.cmd`, панель — http://127.0.0.1:8787/?agents=go. Подробная инструкция и честные границы — [agent/README.md](agent/README.md). Ниже описан прежний браузерный стенд 0.1; его ограничения не следует переносить на новый вариант автоматически.

Собственный локальный proof-of-concept: три независимых виртуальных экрана, простая панель управления, загрузка контента, расписания, offline-кеширование и журнал proof-of-play.

**Это не установленный Xibo и не его форк.** Код написан для этого стенда, без заимствования кода signage-платформ. Вдохновение — типовые сценарии digital signage и архитектура из предоставленных HTML-документов. Демонстрационные изображения и ролик оригинальные.

## Запуск на этом компьютере

1. Дважды нажмите `start-demo.cmd` в папке проекта. Оставьте окно сервера открытым.
2. Откройте **http://127.0.0.1:8787** в обычном окне Chrome или Edge.
3. Дождитесь трёх статусов Online. На чистом браузере плееры сначала загрузят файлы в свой кеш.
4. Останавливайте сервер через Ctrl+C. Повторный запуск сохраняет данные.

На компьютере уже доступен Node.js 24.15.0. Другие компьютеры требуют **Node.js 24 LTS или новее**. `npm install` не нужен: у приложения нет внешних runtime-зависимостей. Предупреждение Node.js о `node:sqlite` на некоторых версиях нормально для этого прототипа.

Альтернативный запуск:

```powershell
npm.cmd start
```

Если порт занят, остановите предыдущую копию. Изменение порта меняет origin браузера: старый IndexedDB-кеш на новом порту недоступен.

## Сценарий показа — 3–5 минут

### 1. Три устройства

На странице «Сеть экранов» покажите:

- экран 01 — плейлист с кофе и городом;
- экран 02 — видеоролик «Идеи в движении» и изображение студии;
- экран 03 — городской цикл.

У каждого собственные device ID, текущий материал, прогресс, кеш и очередь событий. Все iframe используют один компьютер и браузер; это **не три физических устройства и не три Linux-демона**.

### 2. Offline — главный сценарий

1. У экрана 03 нажмите «Отключить связь».
2. Подождите 15–20 секунд: статус станет Offline-кеш, материалы продолжат сменяться, число событий в локальной очереди увеличится.
3. Нажмите «Вернуть связь».
4. Через несколько секунд очередь уменьшится до нуля.
5. В «Журнале показов» выберите экран 03. События имеют исходное время воспроизведения; запоздавшая доставка отмечается отдельно.

Переключатель блокирует **manifest / heartbeat / events API выбранного плеера** ответом 503. Панель и сам сервер остаются доступны. Это управляемая имитация потери связи, а не отключение сетевого адаптера.

Дополнительно можно остановить сервер, **не закрывая браузер**: загруженные плееры продолжают показы из Blob-кеша. Для проверки offline-перезагрузки страницы плеера её Service Worker должен успеть установить и взять страницу под управление. До первого успешного подключения offline-запуск невозможен.

### 3. Управление и расписание

- «Пауза» останавливает видео/таймер изображения, «Продолжить» возобновляет.
- «Далее» завершает текущий показ как interrupted и начинает следующий материал.
- «↻» перезагружает страницу плеера; незавершённый сеанс отмечается interrupted после восстановления.
- «⛶» разворачивает конкретный виртуальный экран.
- «Настроить» позволяет выбрать основной и резервный плейлист, начало/конец интервала.

Без дат основной плейлист играет постоянно. Вне заданного интервала играет резервный. Плеер сам проверяет временное окно локально и продолжает это делать без сервера. Используется время компьютера; синхронизация NTP/RTC пока не реализована. Online-плеер получает изменения примерно раз в две секунды; offline-плеер сохраняет прежнее расписание до восстановления связи.

### 4. Свой контент

1. «Медиатека» → загрузите JPG, PNG, WebP, MP4 или WebM до 1 ГБ.
2. «Плейлисты» → «Новый плейлист» → выберите материалы и длительность.
3. «Сеть экранов» → «Настроить» → назначьте новый плейлист.

Порядок материалов в редакторе фиксирован сверху вниз; свободное переупорядочивание — следующий этап. Длительность — максимальное время показа. Короткое видео завершается по `ended` раньше лимита. Длинное видео обрезается по заданному интервалу. `completed` здесь означает завершение **запланированного интервала**, не обязательно всего исходного файла. Видео без звука. Поддержка MP4 зависит от кодеков браузера; для показа надёжнее использовать готовый WebM.

### 5. Отчёт

«Журнал показов» → «Скачать JSON-отчёт». В UI показываются последние 80 событий; JSON содержит весь журнал. На показе можно открыть раздел «Архитектура»: там явно разделены работающие функции и следующий этап.

## Архитектура

```text
Панель администратора ── HTTP ── Node.js test CMS
                                     │
                                     ├─ SQLite WAL: настройки, плейлисты, PoP
                                     ├─ data/media: пользовательские файлы
                                     └─ public/media: собственные демоматериалы
                           │          │          │
                         HTTP polling, каждые 2 секунды
                           │          │          │
                      screen-01  screen-02  screen-03
                      отдельные browser agents
                      IndexedDB: manifest, Blob-кеш, очередь PoP
                      Service Worker: offline-оболочка плеера
```

Каждый файл перед публикацией нового manifest проверяется по SHA-256. Новое расписание применяется после успешного кеширования всех нужных материалов. При сбое сохраняется прежняя опубликованная версия.

Плеер записывает `started`, `completed`, `interrupted`, `failed`. У события есть UUID; у сеанса показа — отдельный session ID. Очередь удаляется только после ACK сервера. SQLite имеет уникальный ключ event_id, повторная отправка безопасна. PoP фиксируется по событиям браузера и позиции видео; для изображений используется таймер. После аварийного перезапуска восстановленная длительность приблизительна, с последней checkpoint-записи, а не доказательство точного времени сбоя.

Web Locks предотвращает запуск двух активных экземпляров одного device ID в одном browser origin. Поэтому не открывайте второй стенд в соседней вкладке того же браузера: он сообщит, что экран уже занят. Другие профили/браузеры этой блокировкой не защищены.

## Что действительно готово

- три независимых виртуальных плеера и локальная панель;
- видео/изображения, загрузка локальных файлов;
- создание плейлистов, назначение расписаний и fallback;
- персистентные настройки и события на сервере SQLite/WAL;
- персистентный IndexedDB-кеш и PoP-очередь на плеере;
- SHA-256, ACK, дедупликация UUID;
- имитация offline и работа при реальном недоступном сервере;
- пауза, следующий материал, reload, fullscreen;
- отчёт, журнал и фильтры.

## Ограничения — не скрываем на показе

- **Backend на Node.js, не Go.** Go-демон, HTTP/WebSocket-мост и файловый кеш/SQLite на самом устройстве пока не реализованы.
- **Windows/браузерный стенд, не Astra Linux.** Документ руководителя уже предусматривает Astra x86, в том числе Intel N100/N305. Следует уточнить конкретную версию/редакцию Astra, модель мини-ПК и требования к видео.
- Нет MQTT, systemd/watchdog, аппаратного VA-API, OTA, mTLS, настоящего reboot/screenshot.
- `↻` перезапускает страницу, не ОС. Команда хранится как последняя команда; несколько быстро отправленных команд могут заместить друг друга. Полноценная очередь команд пока отсутствует.
- Нет бесшовной гарантии переходов, preload второго видео, докачки больших файлов, лимита/очистки кеша, фонового exponential backoff.
- Backend синхронный, загрузка файла буферизуется в RAM. Это демонстрация, не масштабируемая media ingestion-служба.
- IndexedDB зависит от квоты и политики браузера. Очистка данных сайта удалит кеш плееров, но не серверную SQLite. Приватный режим не рекомендуется.
- Нет авторизации, пользовательских ролей, TLS. Сервер намеренно слушает только 127.0.0.1. **Не публиковать в интернет.**
- Отчёт — показания плеера. Он не доказывает, что физический дисплей включён или что человек видел рекламу. Скрытые iframe/вкладки могут продолжать считать события. Антифрод и контроль видимости — отдельные требования.
- Нет подтверждённой совместимости с API реального заказчика или Xibo.

## Проверки

```powershell
npm.cmd test
```

Серверные тесты: три устройства, offline/API, idempotent PoP, валидация плейлистов/дат, команды, формат загрузки, byte-range, защита Origin, сохранение после restart. Временные тестовые базы изолированы от data/.

Дополнительный полный браузерный прогон требует Playwright и установленного Edge:

```powershell
node tests/browser.mjs
```

На этом компьютере Playwright доступен в bundled runtime; путь можно задать переменной `DOOH_PLAYWRIGHT_MODULE`. Runtime приложения от него не зависит. Браузерный тест создаёт изолированный сервер/БД, проверяет реальные видео, offline, восстановление, расписания, UI и мобильную ширину. Скриншоты сохраняются в test-results/.

`tools/generate-demo-video.mjs` позволяет пересоздать собственный demo WebM через canvas + MediaRecorder, также требует Playwright. Готовый ролик уже включён; для обычного запуска этот инструмент не нужен.

## Файлы

- `server.mjs` — HTTP/API, SQLite, upload и отдача файлов с Range;
- `public/app.js`, `app.css`, `index.html` — панель управления;
- `public/player.js` — браузерный agent и playback;
- `public/db.js` — IndexedDB;
- `public/sw.js` — offline-shell;
- `public/media/` — оригинальные демоматериалы;
- `data/` — серверная база и пользовательский контент (не коммитить);
- `DEMO.md` — короткий текст для презентации.

Следующий технический шаг: перенести обязанности browser agent в Go-демон под Astra x86, сохранив модель manifest и событий. После этого проверить реальные сбои сети/питания, кодеки и аппаратное декодирование на целевом мини-ПК.

## Демонстрационный парк из 100 Go-agent

После запуска Player Server можно поднять 100 независимых Go-agent процессов командой `start-100-go-agents.cmd`. Каждый получает отдельный идентификатор `go-agent-001..100`, HTTP-порт `8891..8990`, собственный каталог SQLite/кеша и отправляет heartbeat и proof-of-play в Player Server. Это нагрузочный демонстрационный режим на одном ПК, а не утверждение о наличии ста физических экранов.

Для переключения с прежнего трёхагентного примера сначала остановите окна `start-go-demo.cmd` и Player Server (Ctrl+C), затем запустите `start-player-server.cmd` и только после этого `start-100-go-agents.cmd`. Панель открывается как `http://127.0.0.1:8787/?agents=go`; после регистрации в ней должны появиться 100 карточек с портами `8891..8990`. Если запускать новый сервер поверх уже занятого `8787`, он завершится с ошибкой `EADDRINUSE`.
