# Отдельный локальный референс Xibo

Это **не DOOH Lab** и не его часть. Здесь установлены Xibo CMS 4.5.2 и сторонний совместимый браузерный `@xiboplayer/pwa` 0.7.23 с `@xiboplayer/proxy` 0.7.23. Источники: [плеер](https://github.com/xiboplayer/xiboplayer), [Docker CMS](https://github.com/xibosignage/xibo-docker).

## Запуск

1. Запустить Docker Desktop и дождаться готовности.
2. Запустить `start-xibo.cmd`. Оставить окно открытым.
3. CMS: http://127.0.0.1:8088 . Новая тестовая установка использует начальные учётные данные из [официальной инструкции](https://account.xibosignage.com/docs/setup/xibo-for-docker): `xibo_admin` / `password`. Это только для локального эксперимента; перед любым расширением доступа пользователь должен сменить пароль.
4. Плеер: **http://localhost:8789/player/**. Адрес `127.0.0.1:8789` не использовать: в версии плеера обнаружение локального прокси проверяет именно hostname `localhost`.

Уже работающий прокси не надо запускать второй раз: порт будет занят. В Chromium/Edge нового профиля плеер потребует подключение заново. CMS URL — `http://127.0.0.1:8088`, CMS Key взять в CMS → Администрирование → Настройки → Конфигурация. Имя — `DOOH Reference 01`. После регистрации в «Дисплеи» разрешить именно этот тестовый дисплей. Другой профиль может создать второй display — это не копия существующего виртуального устройства.

При первом подключении плеер выбирает REST, если доступно, иначе XMDS/SOAP. В этой установке используется XMDS; это не API нашего собственного стенда.

## Нейтральное имя Player Server

CMS на `:8088` — отдельное приложение. Для него добавлена заготовка темы
`theme/PlayerServer` и bind-mount в `compose.yaml`. После перезапуска Docker
стека откройте в CMS **Администрирование → Настройки → Конфигурация** и
выберите тему `PlayerServer`, если она доступна в установленной white-label
сборке. Затем обновите страницу с очисткой кеша (Shift+F5). Если обычный
образ CMS не показывает произвольную папку в списке тем, нужен официальный
white-label архив/сборка Xibo; не пытайтесь менять логотип строковой заменой в
Player Control.

## Подготовленный пример

В медиатеку загружен наш оригинальный `motion.webm` (1280×720). Для `DOOH Reference 01` создано постоянное событие через Библиотека → Объект → More actions у ролика → Расписание → выбрать дисплей → Always → Завершить. Это назначение одного видео, не готовый сложный многороликовый плейлист.

**Проверка 17.09.2026: частично готово.** Вход в CMS работает, ролик виден в библиотеке, дисплей зарегистрирован и разрешён, событие сохранено. После перезагрузки плеер успешно получает RegisterDisplay / RequiredFiles / Schedule по XMDS, но окно остаётся чёрным: элементов видео/изображения в рендере нет. Причина отсутствия воспроизведения пока не установлена. **Не использовать эту связку как основной готовый пример завтра.** Подтверждённый живой пример с видео и тремя плеерами — отдельный DOOH Lab на порту 8787.

Для нового материала: «Добавить медиа» → «Select Files» → выбрать файл → дождаться загрузки → «Готово». Через меню «Расписание» CMS позволяет назначить медиа непосредственно дисплею; воспроизведение такого события конкретным сторонним плеером ещё нужно довести и проверить. Загрузка через автоматизированный браузер заняла около 11 минут — учитывать запас времени.

## Ограничения и безопасность

- Порты CMS, XMR и прокси привязаны только к loopback. Не публиковать установку в интернет и не менять binding на `0.0.0.0`.
- В npm audit выявлено одно уязвимое основание: `pdfjs-dist` и три зависимых пакета помечены high (GHSA-hq66-cqwq-w95j). PDF из неизвестных источников не загружать. Не применять автоматически `audit fix --force`: предложенная замена версии ломает совместимость.
- Авторизация дисплея нужна, но нового внешнего облачного аккаунта не создавалось.
- Не проверены Astra, 48 часов offline, аварийное отключение питания, XMR push и корректность PoP этой сторонней связки.
- XMR контейнер работает, но публичный/WebSocket адрес в CMS не настроен для плеера. Первый пример получает контент по запросам, мгновенные push-команды не обещаем.
- Плеер имеет AGPL-3.0; до включения его кода в решение заказчика проверить лицензионные обязательства.
- Настройки/ключ CMS в `player-data` и npm-зависимости локальные; не пересылать эту папку как публичные исходники.
- CMS хранит базу и библиотеку в именованных Docker volumes; DOOH Lab хранит своё состояние отдельно в `data/`.

## Остановка без удаления данных

Ctrl+C в окне прокси останавливает браузерную серверную часть. Контейнеры CMS можно остановить из папки `reference-xibo`: `docker compose stop`. Следующий `start-xibo.cmd` поднимет их снова. Не использовать `down -v`: это удалит базу и медиатеку референса.
