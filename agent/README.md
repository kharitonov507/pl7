# Нативный плеер — этап 0.2

Это продолжение собственного DOOH-стенда, **не Xibo Player и не Xibo CMS**. Обмен с сервером — наш manifest API, не XMDS. Сервер управления остаётся Node.js; программа **на устройстве** теперь Go.

## Что изменилось простыми словами

Раньше браузер одновременно управлял показом и хранил данные. Теперь обязанности разделены:

```text
Панель и CMS (Node.js, порт 8787)
    │ расписание, медиа, команды; события с подтверждением
    ├─ Go-агент 01 (порт 8791) ─ SQLite 01 + кеш 01 ─ браузерный рендер 01
    ├─ Go-агент 02 (порт 8792) ─ SQLite 02 + кеш 02 ─ браузерный рендер 02
    └─ Go-агент 03 (порт 8793) ─ SQLite 03 + кеш 03 ─ браузерный рендер 03
```

Браузер получает задания через локальный WebSocket, читает медиа с локального HTTP-моста и отправляет сведения о воспроизведении. **IndexedDB и Service Worker в новом рендере не используются.** Если CMS выключена, Go продолжает отдавать свою страницу, расписание и готовые файлы. Если выключен сам Go, рендер не сможет загрузить следующий материал — это другой вид сбоя.

На одном ПК работают три процесса, а не три физических устройства. У каждого отдельные файлы, база и идентификатор.

## Запуск завтра

1. Открой `start-go-demo.cmd` в основной папке проекта. Бинарник уже собран для этого Windows-компьютера. Нужен Node.js 24+.
2. Открой **http://127.0.0.1:8787/?agents=go** в Chrome или Edge. Launcher запускает CMS, если она ещё не работает.
3. Дождись трёх Online. Первый плеер показывает видео и изображение, второй и третий — разные циклы изображений.
4. Оставь окно запуска и вкладку открытыми. Ctrl+C останавливает процессы, запущенные именно этим launcher. На Windows остановка дочернего процесса может быть принудительной: восстановление очереди предусмотрено.

Открывай **одну** панель с этими тремя устройствами: каждый агент допускает только один активный рендер. Вторая панель займёт уже занятые WebSocket-сессии. Для настоящего киоска `chromium` указывается в конфигурации, и браузер запускает сам Go; такой же ID не надо одновременно открывать в панели со встроенным рендером. Отдельный read-only preview киоска ещё не реализован.

Старый вариант сохранён по адресу http://127.0.0.1:8787/ и запускается через `start-demo.cmd`. Его IndexedDB не мигрируется: новые устройства называются `go-screen-01` … `03`. Общая медиатека доступна обоим вариантам. Запуск не сбрасывает прежние настройки устройств.

Если изменился Go-код: сначала останови новый стенд, затем запусти `agent/build-agent.cmd`, потом `start-go-demo.cmd`. В проекте есть переносимый Go SDK в `.tools/go`; системный PATH не менялся. Другой компьютер требует установленного Go и загрузки зависимостей. Собранный агент не требует установленного Go и отдельной библиотеки SQLite.

## Сценарий показа — 5 минут

1. «Теперь показом управляет отдельный Go-процесс. Браузер только рисует».
2. Покажи три плеера и паузу / продолжение / следующий материал.
3. У плеера 03 нажми «Отключить связь». Это **имитация недоступности API данного устройства**, не выдёргивание сетевого кабеля. Показ продолжается, очередь событий растёт.
4. Верни связь. Очередь уменьшается, события появляются в журнале и JSON-отчёте именно Go-устройств.
5. Назначь другой плейлист через «Настроить». Go сначала скачает и проверит файлы, затем применит новое расписание. Вне временного окна локально включается резервный плейлист, даже без CMS.
6. Покажи папку `agent/data/go-screen-03`: `agent.sqlite`, WAL при работающем процессе, `cache` с файлами по SHA-256. Не редактируй работающую базу вручную и не удаляй кеш во время показа.
7. «Это работающий нативный срез. Следующий шаг — проверка на конкретной Astra и мини-ПК, а не заявление о готовом промышленном продукте».

## Возможности и точные границы

| Блок | Что сделано | Что ещё не подтверждено / не сделано |
|---|---|---|
| Go + мост | Отдельные процессы; HTTP медиа/API; WebSocket состояния каждые 200 мс; один рендер | CDP, снимок экрана, настоящая перезагрузка ОС |
| SQLite | WAL, synchronous FULL; manifest, очередь PoP, ID команд, пауза; эксклюзивная блокировка каталога | Поведение при физическом обрыве питания и умирающем накопителе |
| Файловый кеш | Проверка размера и SHA-256; Range-докачивание `.part`; публикация после проверки; квота | CDN/S3, несколько параллельных загрузок, скорость/стоимость трафика |
| Расписание | Основной / резервный; проверка окна по часам устройства | NTP/RTC и гарантия ±500 мс; сейчас её нет |
| Proof-of-play | started/completed/interrupted/failed; очередь до ACK; повторная доставка без дублей | Физический экран/аудитория; скрытая вкладка не считается нормальным показом; 48-часовой тест |
| Chromium | Kiosk, отдельный профиль, supervisor, перезапуск принадлежащего агенту процесса при отсутствии heartbeat | Реальный Chromium под Astra, доступ к графической сессии, GPU и sandbox на целевой ОС |
| systemd | sd_notify READY/WATCHDOG/STOPPING; SIGTERM; шаблон user-service | Установка/проверка службы на Astra; аппаратный watchdog |
| MQTT | QoS 1 команды, прикладной ACK, постоянная дедупликация, LWT, телеметрия; TLS для удалённого брокера | Production-брокер, индивидуальные credentials/ACL, expiry/порядок/полная очередь команд CMS |
| Авторизация | Токен локального моста, HttpOnly/SameSite-cookie, Host/Origin; опциональный bootstrap Bearer Go → CMS | Пользовательский вход и роли CMS, индивидуальные токены/отзыв, mTLS, аудит безопасности |
| OTA | Ed25519-подпись, SHA-256/размер, OS/arch, sequence anti-replay; загрузка `.candidate` | Установка, атомарная смена бинарника, health-gate, A/B-откат; **это не полный OTA** |
| Мониторинг | Статус в панели, `/health`, защищённый `/metrics` в формате Prometheus, MQTT telemetry | Настроенные Prometheus/Grafana/alerts, журнал действий пользователей |

`completed` означает конец ролика либо достижение заданного максимума показа, а не обязательно просмотр всего исходного видео. Переходы не заявляются бесшовными. После обрыва рендера предыдущая сессия завершается как interrupted; создаётся новая. После аварии Go playedMs берётся из последнего сохранённого checkpoint, а occurredAt — время восстановления: это не точное время аварии. Изображения сохраняют checkpoint примерно раз в секунду; видео — при отчётах рендера. Отчёты не являются независимым доказательством физического вывода.

### Квота и докачивание

По умолчанию 512 МиБ **на кеш одного агента**, включая `.part`, но не SQLite, browser profile, MQTT spool и OTA-кандидаты. Старые неприкреплённые hash-файлы удаляются по времени изменения. Основной и резервный опубликованные наборы защищены, как и уже подготовленные файлы нового набора. Если одновременно старый и новый наборы не помещаются — обновление не публикуется, старый показ остаётся. Для перехода нужна свободная ёмкость, а не только размер нового набора. Учёт всего диска, ограничение очереди событий и очистка OTA-кандидатов — последующая работа.

Незавершённый файл получает расширение `.part`. При следующем обмене Go запрашивает оставшиеся байты. Если сервер игнорирует Range и отвечает 200, файл скачивается заново. Неверный SHA-256 не публикуется. Все пути кеша строятся из проверенного hash, не из пользовательского имени.

### Локальный мост и токены

Мост слушает только loopback IP. `/api/*`, `/media/*`, `/ws`, `/metrics` требуют Bearer либо cookie. Открытие собственной страницы выдаёт cookie; браузерный JavaScript не читает токен. Проверяются Host и Origin, отсекается cross-site bootstrap. Cookie уникальна для каждого устройства, поскольку cookie не разделяются по портам.

Это защита от посторонней веб-страницы, **не от скомпрометированного локального пользователя**. Приложение с доступом к файлам или локальному HTTP может получить токен. Панель CMS остаётся без пользовательского входа, локальные HTTP-медиа не секретны. Стенд не публикуется в интернет.

Опционально одинаковая переменная окружения `DOOH_CMS_TOKEN` в launcher/CMS и Go защищает регистрацию и manifest/events/heartbeat новых Go-устройств. Она не включает авторизацию административной панели. Если CMS уже запущена с другим окружением, её надо корректно перезапустить; переменная не меняет работающий процесс. Секреты не кладут в Git и не выводят в отчёт.

`restart` сейчас начинает новую сессию воспроизведения, а не перезагружает ОС. Для полного kiosk-рестарта предусмотрен supervisor, но команда CMS его ещё не вызывает.

## MQTT — отдельный локальный эксперимент

По умолчанию отключён, основной сценарий использует HTTP и работает без Docker.

```powershell
docker compose -p dooh-native-lab -f agent/mqtt-demo/compose.yaml up -d
```

В конфигурации агента можно задать `mqttBroker: tcp://127.0.0.1:18884` и уникальный topic `dooh/lab/go-screen-01`. Launcher передаёт уникальные topics для всех трёх. Команда — JSON `{"commandId":"unique-id","action":"pause"}` в `<topic>/cmd` с QoS 1 и **без retain**. Ответ `<topic>/ack` означает, что агент обработал ID команды и сохранил состояние. ID нельзя повторно использовать для другой команды. Доступны pause/resume/next/restart. Старые retained сообщения на подписке игнорируются; механизм TTL ещё не реализован.

Лабораторный брокер анонимный, доступен на loopback и не сохраняет данные. Для удалённого адреса агент требует ssl/tls/wss, проверяет сертификат и TLS 1.2+. Credentials задаются `DOOH_MQTT_USER`, `DOOH_MQTT_PASSWORD`, пользовательский CA — `mqttCA`. Production-брокер обязан ограничивать topic каждого устройства. Сейчас CMS не публикует команды в MQTT автоматически — проверен канал агента, не полный MQTT workflow платформы.

Остановка только этого лабораторного брокера:

```powershell
docker compose -p dooh-native-lab -f agent/mqtt-demo/compose.yaml down
```

## Linux / Astra: безопасный следующий запуск

Собран `agent/bin/dooh-agent-linux-amd64` без CGO. ARM64 можно собрать отдельно, но архитектурный документ ориентирует на x86; тип процессора и точная версия Astra должны быть подтверждены. Linux unit-тесты выполнены в контейнере, **не в Astra и не на экране**.

Не устанавливаем службу и не меняем системные настройки без выбранного устройства. Шаблон `linux/config.template.json` содержит заведомо нерабочий адрес `cms.example.invalid`: его, username, путь к данным и Chromium нужно заменить. Linux-агент использует наш API; к Xibo CMS его нельзя подключить просто заменой URL. Удалённый сервер обязан быть HTTPS.

Шаблон `linux/dooh-agent.service` — **пользовательская systemd-служба** в существующей графической сессии. Бинарник предполагается в `/opt/dooh/bin`, конфигурация в `~/.config/dooh/agent.json`, секреты — `agent.env` с правами 0600. Рабочий каталог данных должен принадлежать пользователю, запускающему плеер. Chromium не запускается root и флаг `--no-sandbox` не применяется. Нужно проверить поддержку sandbox в конкретной Astra, а не обходить её отключением.

На выбранной Linux-машине сначала запуск вручную и журнал, затем проверка графической сессии, только потом служба:

```sh
systemd-analyze --user verify ~/.config/systemd/user/dooh-agent.service
systemctl --user daemon-reload
systemctl --user start dooh-agent
systemctl --user status dooh-agent
journalctl --user -u dooh-agent -f
```

Если окружение Astra не активирует graphical-session.target или не экспортирует DISPLAY/XAUTHORITY/Wayland-окружение в user manager, шаблон нужно адаптировать к её штатной сессии. Не угадывать DISPLAY и не копировать чужие файлы авторизации. Автозапуск включать после успешной проверки; конкретный способ зависит от desktop/session. User-service не гарантирует запуск киоска до входа пользователя. Аппаратный watchdog и autologin — отдельно согласуемые настройки ОС, не часть текущего Windows-демо.

### Проверка аппаратного декодирования

Нужны точная Astra/build, Chromium/version, Intel GPU/driver, разрешение и реальные кодеки файлов. Проверить доступ к `/dev/dri`, результат `vainfo`, `chrome://gpu` и **конкретный проигрываемый ролик** в `chrome://media-internals`. Наличие GPU в системе не доказывает, что ролик декодируется аппаратно. Не добавлять случайный набор VA-API flags: они зависят от сборки и версии. Наш WebM-пример не доказывает H.264/HEVC/4K на мини-ПК. [Официальная инструкция Chromium по VA-API](https://chromium.googlesource.com/chromium/src/+/HEAD/docs/gpu/vaapi.md).

Приёмка на железе: старт после включения; связь offline → online; перезапуск CMS/Go/Chromium; watchdog; реальное отключение питания на подготовленном тестовом носителе; длительный offline 48 часов; квота/нехватка диска; валидный и битый файл; ошибка обновления и откат после его реализации; температурная нагрузка и пропуски кадров. До этого не обещать промышленную готовность.

## OTA: что можно попробовать уже сейчас

CLI `-stage-ota <signed-manifest.json>` проверяет подписанный манифест и скачивает кандидат. На время этого режима штатный агент с тем же каталогом данных надо остановить: база защищена эксклюзивной блокировкой. В `otaPublicKey` должен быть заранее доверенный публичный Ed25519-ключ. Приватный ключ хранится вне устройства и репозитория.

Envelope содержит base64 `payload` и `signature`, подписаны **исходные байты payload**. Payload: version, монотонный sequence, os, arch, url, sha256, size. Не принимаются неверная подпись, другая платформа, повторный sequence, неподходящий размер и hash. URL должен быть HTTPS либо лабораторный loopback HTTP. По завершении сохранится `.candidate`, а не заменится работающая программа. Встроенные тесты создают временный ключ и проверяют этот путь; никакой тестовый ключ не установлен как production-доверенный. Удалённый запуск этого режима через CMS/MQTT пока не подключён.

## Проверки разработчика

Из основной папки `npm.cmd test`: 8 проверок CMS, включая регистрацию Go и опциональный токен. Из `agent`:

```powershell
..\.tools\go\bin\go.exe test -v ./...
..\.tools\go\bin\go.exe vet ./...
$env:DOOH_TEST_MQTT='tcp://127.0.0.1:18884'
..\.tools\go\bin\go.exe test -run TestMQTTLive -v
$env:DOOH_TEST_AGENT_BINARY='bin/dooh-agent.exe'
..\.tools\go\bin\go.exe test -run TestNativeProcess -v
```

Без `DOOH_TEST_MQTT` интеграционная проверка брокера пропускается. Без `DOOH_TEST_AGENT_BINARY` не запускается отдельный бинарный процесс. Проверки используют временные каталоги, не рабочие базы. Блокировка каталога не даёт двум агентам одновременно писать одну базу. Зависимости фиксированы `go.mod`/`go.sum`: [modernc SQLite](https://pkg.go.dev/modernc.org/sqlite), [coder WebSocket](https://pkg.go.dev/github.com/coder/websocket), [Eclipse Paho MQTT](https://pkg.go.dev/github.com/eclipse/paho.mqtt.golang).
